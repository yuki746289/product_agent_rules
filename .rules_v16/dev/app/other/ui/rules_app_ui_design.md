# UIデザイン追加ルール

## 1. 目的

参照画像、モックアップ、ワイヤーフレームまたは既存画面を基準とするUI開発で、機能だけを維持して見た目の要件を縮小することを防ぎます。

## 2. 適用条件

次のいずれかに該当する場合、通常開発の`app`に追加分類`ui-design`を適用して下さい。

- 参照画像、モックアップまたはワイヤーフレームが提示されている。
- HTML、CSS、画面構造、ブランド表現、キャラクター配置またはレスポンシブ構造を変更する。
- ユーザが参照画面との一致、再現またはデザイン変更を求めている。

単一プロパティ、文言または表示・非表示だけを変更し、仕様と画面構造を変更しない場合は`quick_fix`を使用できます。ただし参照画像との再現度が完了条件に含まれる場合は`ui-design`を使用して下さい。

## 3. 開始時の宣言

作業開始時に次を記録して下さい。

- 開発種類: `app`
- 追加分類: `ui-design`
- 参照資料のパスまたはURL
- 再現度: A / B / C
- 対象画面と対象外画面

|再現度|意味|許容される差異|
|---|---|---|
|A|高再現|実データ、利用可能素材および既存機能による不可避な差異だけを許容する。|
|B|構造再現|情報階層、主要配置、視線誘導、相対寸法およびレスポンシブ構造を再現し、装飾の軽微な差異を許容する。|
|C|参考|配色や雰囲気だけを参考にし、構造の変更を許容する。|

再現度が未指定で実装結果を大きく左右する場合はユーザへ確認して下さい。参照資料同士または既存仕様と矛盾する場合も、独自に縮小解釈せず作業を停止して下さい。

## 4. 機能維持とレイアウト維持

「既存機能を変更しない」は、既存処理、URL、データ構造および操作結果を維持する指示です。参照画像で要求されたDOM順序、情報階層、主要配置または外観を維持しなくてよいという意味ではありません。

次を別々に判定して下さい。

- 機能・データ・URLの維持
- DOM・レイアウト・視覚表現の変更
- 既存機能回帰の有無
- 参照資料との視覚差異

### 4.1 承認済みサンプル正本方式

最終承認されたサンプルのHTML、CSS、画像および画面幅別スクリーンショットを、対象画面の構造と視覚表現の正本として扱って下さい。既存コードを正本へ近づけるのではなく、正本の構造を基礎にして、既存のid、JavaScript、API、URL、データ表示および操作イベントを接続します。

機能維持は、古いDOM構造や視覚表現の維持を意味しません。正本に存在しない既存機能を残す場合は、正本の情報階層を壊さない追加位置を決め、追加理由と確認方法を記録して下さい。

### 4.1.1 正本追加前の不足確認

実装前に、正本へ接続または追加するものをUI追加要件ID（`UIA001`等）で整理して下さい。

|UI追加要件ID|画面|正本の要素|不足する既存機能・情報|接続先id/class|関連JavaScript/API/URL|追加位置|追加方法|削除する旧DOM/CSS|影響ブロックID|確認幅・状態|判定|
|---|---|---|---|---|---|---|---|---|---|---|---|
|UIA001||||||||||||

不足確認を完了せずに正本へ既存コードを継ぎ足してはいけません。追加後は、全UI追加要件IDについて機能確認と視覚確認を別々に実施して下さい。

## 5. 参照資料の要素分解

要件定義前に、参照資料を次の表へ分解して下さい。参照画像が複数ある場合は画像ごとに識別子を付けて下さい。

|UI要件ID|参照位置|期待する要素・配置|現状|変更区分|必要素材|許容差異|確認方法|
|---|---|---|---|---|---|---|---|
|UI001|例: ホーム上部|例: 主見出し、説明、人物画像、CTAを一体化したヒーロー|未対応|ADD / MOD / KEEP / DEL|画像、アイコン|再現度に従う|画面幅別スクリーンショット|

次を必ず確認して下さい。

- 画面全体の情報階層
- ヘッダ、ヒーロー、本文、CTA、カード、フォーム、フッタの順序
- 文字、画像、余白、枠、背景および装飾の相対的な大きさ
- PCとモバイルでの並び替え、縮小、非表示および折り返し
- 参照画像にだけ存在する機能を追加するか、表示だけ再現するか
- 既存画面にだけ存在する機能をどこへ保持するか

### 5.1 確認ブロックID方式

ページをヘッダ、ヒーロー、ナビゲーション、検索、カード一覧、本文、CTA、フッタ、固定ボタン等の確認単位へ分け、重複しない確認ブロックID（`UIB001`等）を付与して下さい。確認ブロックIDは検証記録用であり、HTMLの`id`属性とは別に管理します。必要な場合だけ`data-ui-block-id`としてDOMへ付与して構いません。

|確認ブロックID|画面|ブロック名|参照元|対象DOM/CSS|確認する幅・状態|共通/固有|備考|
|---|---|---|---|---|---|---|---|
|UIB001||||||||

修正、比較結果、差異、再確認および承認は、確認ブロックID単位で追跡して下さい。共通部品を修正した場合は、その部品を使用する全ページを影響範囲に含めます。

## 6. 素材実現性確認

基本設計前に必要素材を棚卸しして下さい。

- 既存素材のパス、解像度、透過、トリミング可否
- 新規作成が必要な素材
- ライセンスまたは利用制限
- 参照画像どおりに再現できない要素と代替案

素材不足のまま、参照画像の主要構造を別デザインへ置き換えて実装を進めてはいけません。

## 7. 基本設計とプレビュー承認

基本設計には、画面単位のレイアウト図、DOMの大区分、PC・モバイルの配置、共通コンポーネント、既存機能の配置先およびUI要件IDを記載して下さい。

独自レイアウトまたは主要画面種別ごとに、実装前プレビューを作成して下さい。プレビューは静的HTML、画像または既存コードを使用しない確認用画面で構いません。

手順5の完了条件に、次を追加します。

- ユーザがプレビューを確認している。
- 参照資料との主要差異が説明され、承認されている。
- 未承認の主要差異が0件である。

承認前に詳細設計または本実装へ進んではいけません。

## 8. 詳細設計

詳細設計には次を記載して下さい。

- UI要件IDと対象HTML、CSS、JavaScript、画像の対応
- DOM順序と主要クラス名
- PCとモバイルの表示条件
- 主要寸法、相対寸法、余白、重なり順および画像トリミング
- hover、focus、active、展開・縮小状態
- 既存機能を保持する配置とイベント
- 実装しない参照要素と理由
- 画面幅別の確認方法

## 9. 実装開始前確認

実装前に、参照資料、再現度、要素分解表、承認済みプレビュー、詳細設計、素材、UI追加要件IDおよび確認ブロックIDの対応が揃っていることを確認して下さい。要件を「共通ガイドを追加する」など一部分だけへ縮小してはいけません。

## 10. 画面確認

実装後は実際のアプリケーション画面で確認して下さい。静的プレビューだけで完了してはいけません。

最低限、次を確認して下さい。

- 指定された全画面幅
- 横スクロール、重なり、はみ出し、トリミング
- 主要な情報階層と視線誘導
- CTA、フォーム、フィルタ、地図操作部品等との衝突
- hover、focus、active、展開・縮小状態
- 既存機能回帰
- 参照資料との並列比較または注記付き比較

「横スクロールがない」「機能が動く」だけで視覚確認を合格にしてはいけません。

### 10.1 正本対応表とページ別確認ファイル

比較元は、ページ、URL、表示状態および画面幅ごとに最終承認された正本を特定して下さい。途中版や別ページの画像を代用してはいけません。

- `app_ui_design_confirm.md`は案件全体の索引と総合判定に使用する。
- ページごとに`{page_identifier}_ui_confirm.md`を作成し、正本、確認ブロックID、幅別結果および証跡を記録する。
- 複数ページで同じヘッダ、フッタ、固定ボタン等を確認する場合は、`common_ui_confirm.md`へ共通結果を集約してよい。
- ページ別確認を省略して、案件全体の1ファイルだけで合格にしてはいけない。

指定がない場合の必須確認幅は、`320px`、`375px`、`414px`、`799px`、`800px`、`801px`、`1024px`、`1366px`です。通常、hover、focus、active、展開、縮小、読み込み中、データなし、最大件数等、対象画面で成立する状態も確認して下さい。

### 10.2 実ブラウザ・配信元・比較条件

実際に配信されるアプリケーションをブラウザで開き、次を証跡へ記録して下さい。

- URL、環境名、commit SHAまたはビルド識別子、確認日時
- `window.innerWidth`、`window.innerHeight`、ズーム100%、devicePixelRatio、向き、スクロール位置
- CSS/JavaScript/画像の配信元と更新時刻、キャッシュ、Service Worker、起動中サーバおよび古いビルドの混入有無
- headlessと通常ブラウザで異なる可能性があるフォント、スクロールバー、画像描画および操作状態

正本、実装結果、並列比較画像は同じ幅、状態、ズームおよびスクロール位置で保存して下さい。比較画像のどちらが正本か、どちらが実装結果かをファイル名または画像内ラベルで明示します。

### 10.3 機械検査・機能試験・視覚確認

次の判定を混同せず、個別に記録して下さい。

1. 機械検査: `scrollWidth`と`innerWidth`、`getBoundingClientRect()`、要素間重なり、クリッピング、固定要素位置、画像の自然寸法と表示寸法を確認する。
2. 機能試験: CTA、リンク、フォーム、地図、展開・縮小、ページング等の操作結果を確認する。
3. 視覚確認: 正本とブロック単位で、位置、寸法、余白、色、フォント、画像比率、トリミング、重なり順を比較する。
4. ユーザ目視: 機械検査・機能試験・視覚確認の合格後、ユーザが実ブラウザで最終確認する。

画像差分率だけで合格にしてはいけません。差分が意図した動的データか、実装差異かを確認ブロックID単位で判定して下さい。修正後は変更したブロックだけでなく、影響する共通ブロック、全必須幅および関連状態を再確認します。

## 11. 完了条件

次を全て満たした場合だけ完了できます。

- 全UI要件IDが実装済み、承認済み差異または対象外として説明されている。
- 未承認の視覚差異が0件である。
- 画面幅別スクリーンショットが保存されている。
- 参照資料との比較結果が記録されている。
- 既存機能回帰がない。
- ユーザが最終画面を目視確認し、承認している。
- ページ別確認ファイルおよび必要な共通確認ファイルが全てPASSである。
- 全UI追加要件IDと確認ブロックIDが、実装、対象外または承認済み差異として説明されている。
- 必須8幅と対象状態について、実ブラウザ情報、配信元確認、機械検査、機能試験および視覚確認が個別に記録されている。
- 正本と実装結果を識別できる並列比較画像が保存されている。

## 12. 確認ファイル運用

作業開始時に`.rules/dev/app/other/ui/app_ui_design_confirm.md`を案件の成果物フォルダへコピーし、案件情報、適用条件、参照資料および再現度を記録して下さい。主ファイルを索引として、対象ページごとの`{page_identifier}_ui_confirm.md`と、必要に応じた`common_ui_confirm.md`を同じ成果物フォルダへ作成して下さい。

確認ファイルは少なくとも次のタイミングで更新して下さい。

- 仕様書と仕様確認の完了時
- 基本設計と実装前プレビューの承認時
- 詳細設計と詳細設計確認の完了時
- コード確認時
- 実画面の最終目視承認時

未確認、未完了またはNGの項目が残る場合は、該当工程および最終確認をPASSとしてはいけません。該当しない項目は空欄にせず、`N/A（理由）`を記録して下さい。レビューまたはユーザ指示による修正後は、影響する項目と証拠を更新して再確認して下さい。
