# product_agent_rules

AI エージェント向けの開発・確認ルールを管理するためのリポジトリです。

複数バージョンの `.rules_*` ディレクトリを保持し、別プロジェクトでは必要なルールセットを `.rules` として取り込んで利用します。

## 使用準備

### 手順1. 取り込み先プロジェクトへルールを配置する

別プロジェクトへ取り込む場合は、`pull_rules.sh` を実行してください。

最新版の `.rules_v15` が、取り込み先リポジトリでは `.rules` という名前で配置されます。

### 手順2. AI エージェント用の指示を追加する

取り込み先プロジェクトの `AGENTS.md` など、AI エージェントが参照する指示ファイルには、以下を追加してください。

```markdown
- 開発・分析ルール
  - 開発または分析を行う場合、必ず`.rules/dev/rules_dev.md`を確認すること。
```

プロジェクト固有のルールは `.rules/dev/rules_dev_custom.md` に記載します。デフォルトは空です。`pull_rules.sh` でルールを更新しても、取り込み先にあるこのファイルの内容は保持されます。

## 使用方法

### 簡単な使用例

依頼前に、通常開発、簡易開発または分析を選びます。
v15 の通常開発では、最初に仕様書を作成・確認し、その後に要件定義、設計、実装、最終確認を行います。参照画像等を扱うapp開発では`ui-design`、既存実装を置き換えるappまたはbatch開発では`replace`追加分類を使用します。HTML、CSS、JavaScript、Java、SQLを作成または変更する場合は、appまたはbatchの言語別コード実装規約と `*_confirm.md` を使用します。

- `app`: アプリケーション向けの通常開発ルールです。仕様作成から実装後の最終確認までを扱います。
- `app + ui-design`: 参照画像、モックアップ、画面構造またはレスポンシブデザインを扱うapp開発です。再現度、UI要件ID、実装前プレビュー、画面比較およびユーザ目視承認を追加管理します。
- `app + replace`: 既存アプリケーションの実装、基盤、状態管理または連携方式を置き換えるapp開発です。外部契約、移行、切替、復旧、ロールバックおよび旧実装の廃止を追加管理します。
- `app + replace + ui-design`: UIを含むappリプレースです。appリプレースとUIの両方のルールおよびチェックリストを使用します。
- `app + performance`: 起動、初期表示、操作応答、メモリ、I/Oまたは大量データ処理を改善するapp開発です。`app/other/performance/`のルールとチェックリストを使用します。
- `batch`: バッチ処理やスクリプト向けの通常開発ルールです。仕様作成から実装後の最終確認までを扱います。
- `batch + replace`: 言語、ライブラリ、module、処理基盤または実行方式を置き換えるbatch開発です。基準入出力、全件同値、再実行、性能、切替、復旧および旧実装の廃止を追加管理します。
- `batch + performance`: 大量データ、長時間処理、メモリ、I/O、分割・並列または再計算を改善するbatch開発です。`batch/other/performance/`のルールとチェックリストを使用します。
- `class`: クラス設計向けの通常開発ルールです。現在作成中のため、利用時は内容を確認してください。
- `quick_fix`: 既存仕様を変更しない軽微な修正向けの簡易開発ルールです。仕様変更や仕様書修正が必要な場合は使用できません。
- `analyze`: GitHub Actionsを原則として一括分析を行うルールです。全体ワークフロー、分割・並列、public/private分離、定期通知、終了予定およびChatGPT分析のGit管理を扱います。
- `analyze + performance`: 分析処理の測定、数値同値、checkpointおよび性能監査を扱います。分析では`.rules/dev/performance/`の既存ルールとチェックリストを使用します。
- Pythonコードを作成・変更する場合、appは`app/rules_app_8_code/`、batchは`batch/rules_batch_8_code/`のPythonコード実装規約を参照し、同じフォルダの `*_python_confirm.md` を案件へコピーします。Pythonでは共通規約のcamelCase・C系コメント例ではなく、Python規約のsnake_case・`#`・Python用headerを優先します。
- HTML、CSS、JavaScript、Java、SQLを作成・変更する場合も、同じフォルダの言語別規約と `*_confirm.md` を使用します。共通規約のcamelCase例、コメント例またはheader例と異なる場合は、言語別規約を優先します。画面のレイアウト、id、class、共通枠、読込順およびレスポンシブは、HTML規約とCSS規約を優先します。

依頼例:

```text
.rules/dev/rules_dev.md を確認してから進めてください。
今回は app ルールを使用します。
対象は sample_app です。
○○を作成したいです。
```

### 開発成果物の標準配置

v15では`.document`を単数形の正式名称とし、全体仕様と開発案件を分けて管理します。

```text
.document/
└─ v{n}.{m}/
   ├─ 00_全体仕様/
   │  ├─ 00_index.md
   │  ├─ 01_差分仕様.md
   │  ├─ 項目別仕様書
   │  └─ 99_仕様確認.md
   └─ 01_開発案件/
      ├─ 00_開発案件一覧.md
      ├─ 01_完了/
      └─ 02_未完了/
         └─ {NN}_{案件名}_v{n}.{m}/
```

- 通常開発の手順1〜2は`00_全体仕様/`へ格納します。
- 通常開発の手順3〜10とquick_fixの手順1〜3は案件フォルダへ格納します。
- 合格した案件だけを`02_未完了/`から`01_完了/`へ移動します。
- `00_開発案件一覧.md`を案件番号、工程、状態、ブランチ、commitおよび証跡の正本とします。
- 案件番号は2桁で採番し、完了、取消または統合後も変更・再利用しません。
- `.document/v{n}.{m}`はリリース番号ではなく全体仕様の基準版です。アーキテクチャ等の主要前提変更はmajor、同じ主要構造内の全体仕様変更はminorを更新し、案件追加・実装修正・証跡追加だけでは更新しません。

## ルールセットのバージョン管理

ルールセットの命名・更新は [RULE_VERSIONING.md](RULE_VERSIONING.md) に従います。

- ディレクトリ名は `.rules_v{n}` とし、`n`は1から始まる10進整数を使用します。
- `.rules_v01`のようなゼロ埋めは使用しません。
- GitHubの一覧は文字列順のため、`.rules_v10`が`.rules_v1`と`.rules_v2`の間に表示されることを許容します。
- 最新版は表示順ではなく、数値として最大のバージョン番号で判断します。

## ルールの取り込み

取り込み先のリポジトリで `pull_rules.sh` を実行します。

```bash
bash ./pull_rules.sh
```

既定では `yuki746289/product_agent_rules` から取得します。

### 取り込み対象

スクリプトを実行すると、取得元リポジトリにある `.rules_v15` の各項目が `.rules` へ配置されます。

```text
.rules_v15/* -> .rules/*
```

### 上書き確認

取り込み先に同名のファイルまたはディレクトリがある場合は、項目ごとに置換確認メッセージが表示されます。

```text
Replace '.rules/dev'? [y/yes/n/no]:
```

`y` または `yes` を入力すると、対象項目を削除してから `.rules_v15` の同名項目をコピーします。

`n` または `no` を入力すると、その項目をスキップして次の項目へ進みます。

### 注意

- `.rules` 直下の項目単位で置換されます。
- 取得元に存在しないローカル専用項目は保持されます。
- 置換をスキップした項目には、旧バージョンのファイルが残る場合があります。
- 取り込み後は `git status --short` や `git diff --stat` で差分を確認してください。
