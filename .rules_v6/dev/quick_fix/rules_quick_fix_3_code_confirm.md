# 簡易修正 手順3: コード確認

作成日時: 2026-05-19 08:03:22

## 目的

  手順2で修正したコードについて、修正内容、影響範囲、動作確認結果を確認します。
  手順1で承認された修正内容と、手順2のコード修正が一致していることを確認します。

## 参照ルール

  - `.rules/rules_common.md`
  - `.rules/dev/rules_dev.md`
  - `.rules/dev/quick_fix/rules_quick_fix_1_request.md`
  - `.rules/dev/quick_fix/rules_quick_fix_2_code.md`
  - `.rules/dev/quick_fix/rules_quick_fix_3_code_confirm.md`
  - 手順1で承認済みの `{filename}_v{n}.{m}_1_request.md`
  - 手順2で作成した `{filename}_v{n}.{m}.{code_ext}`

## 入力

  - 手順1で承認済みの修正内容の要件
  - 手順2で修正したコードファイル
  - 直前バージョンまたは直前リビジョンのコードファイル
  - 動作確認結果

## 出力

  `{filename}_v{n}.{m}_3_code_confirm.md`

## 作成内容

  以下を記述します。

  - 確認対象ファイル
  - 修正内容の概要
  - 修正差分
  - 手順1の要件との対応
  - 影響範囲
  - 動作確認内容
  - 動作確認結果
  - デグレ確認結果
  - 仕様書作成の要否
  - 仕様書作成を省略する場合の理由
  - 残課題
  - ユーザ確認事項

## 確認観点

  以下を確認します。

  - 手順1で承認された範囲内の修正であること
  - 修正対象ファイルが正しいこと
  - 修正差分が必要最小限であること
  - 不要な機能追加がないこと
  - 不要なリファクタリングがないこと
  - 既存の入出力仕様を不要に変更していないこと
  - 既存の処理フローを不要に変更していないこと
  - 既存のID体系を不要に変更していないこと
  - 既存の `[KEEP]` ロジックを変更していないこと
  - 実装可能な内容として成立していること
  - 動作確認が実施されていること
  - 仕様への影響があるか確認していること
  - 仕様書作成を省略する場合、省略理由が妥当であること

## 動作確認

  以下を記述します。

  - 実施した確認内容
  - 使用したコマンド
  - 使用した入力データ
  - 期待結果
  - 実際の結果
  - 確認結果
  - 動作確認できなかった場合の理由

## 仕様書作成の要否

  以下を記述します。

  - 仕様への影響の有無
  - 仕様書作成が必要か不要か
  - 仕様書作成を省略する場合の理由
  - 手順4および手順5を省略する場合、ユーザへ報告した内容

## 通常開発へ切り替える条件

  コード確認中に以下が判明した場合は、作業を停止し、ユーザに報告します。

  - 手順1の範囲を超える修正が行われている場合
  - 基本設計または詳細設計の変更が必要な場合
  - 複数機能に大きく影響する場合
  - 入力仕様、出力仕様、DB仕様、ファイル仕様が大きく変わる場合
  - 既存の `[KEEP]` ロジックに影響している場合
  - 動作確認方法を定義できない場合
  - 実装可能な内容として成立していない場合

## 注意事項

  - 確認開始前に、参照ルールと参照ファイルを提示すること。
  - 修正差分を明記すること。
  - 動作確認結果を明記すること。
  - 動作確認できない場合は、理由を明記すること。
  - 仕様書作成を省略する場合は、理由を明記し、手順4および手順5を省略することをユーザへ報告すること。
  - 不明点や矛盾がある場合は作業を停止し、ユーザに確認すること。
