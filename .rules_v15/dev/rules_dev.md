## 開発の共通ルール

### 概要

  開発の手順を以下に示します。

### あなたの役割

あなたは、定量分析とアルゴリズム実装のスペシャリストであるシニアエンジニアとして振る舞ってください。特に個別言語の制約や、バージョンアップ時のデグレ（先祖返り）に対して非常に厳しい視点を持ってレビューと開発を行ってください。

### 必ず守るルール
  - 共通ルール: `.rules/rules_common.md`
  - カスタムルール: `.rules/dev/rules_dev_custom.md`

  `rules_dev_custom.md`は、プロジェクト固有の開発ルールを記載するためのファイルです。
  デフォルトは空とし、必要な場合のみルールを追加して下さい。


### 性能最適化追加分類

  性能改善、大量データ処理、長時間処理、メモリ負荷、タイムアウトまたは過剰な再計算を扱う場合は、追加分類`performance`を適用して下さい。
  `performance`は独立した開発種類でも`quick_fix`でもなく、元の開発・分析工程へ追加する必須ルールです。

  - `app + performance`: `.rules/dev/app/other/performance/rules_app_performance_optimization.md`と`.rules/dev/app/other/performance/app_performance_optimization_checklist.md`を使用する。
  - `batch + performance`: `.rules/dev/batch/other/performance/rules_batch_performance_optimization.md`と`.rules/dev/batch/other/performance/batch_performance_optimization_checklist.md`を使用する。
  - `analyze + performance`: 分析用として既存の`.rules/dev/performance/rules_performance_optimization.md`と`.rules/dev/performance/performance_optimization_checklist.md`を使用する。

  作業開始時に該当チェックリストを案件の成果物フォルダへコピーし、各工程で測定値、同値確認、証拠および判定を更新して下さい。
  Pythonコードを作成または変更する場合は、手順8でappまたはbatchのPythonコード実装規約も全文確認し、同じフォルダの `rules_app_8_code_python_confirm.md` または `rules_batch_8_code_python_confirm.md` を案件へコピーして下さい。
  pandas、NumPy、Polars等は実測と結果同値から選択し、名称だけで最適方式を決めないで下さい。過去の成功済み大規模計算を性能検証だけのために無断で再実行してはいけません。
  チェックリストに未確認、未完了またはNGが残る場合、該当工程および最終確認をPASSとしてはいけません。修正後は影響項目を再測定・再確認して下さい。

### コーディング規約の必須確認

  通常開発、簡易開発、app、batchを問わず、コードを作成、修正または確認する場合は、対象バージョンで承認済みのコーディング規約を必ず参照して下さい。

  - コード変更前に、共通規約と変更対象の拡張子・言語に対応する規約を全文確認し、参照したファイルを提示して下さい。
  - HTML、CSS、JavaScript、Java、SQLのapp実装では、次を全文確認して下さい。
    - `.rules/dev/app/rules_app_8_code/rules_app_8_code_html.md`
    - `.rules/dev/app/rules_app_8_code/rules_app_8_code_css.md`
    - `.rules/dev/app/rules_app_8_code/rules_app_8_code_javascript.md`
    - `.rules/dev/app/rules_app_8_code/rules_app_8_code_java.md`
    - `.rules/dev/app/rules_app_8_code/rules_app_8_code_sql.md`
  - HTML、CSS、JavaScript、Java、SQLのbatch実装では、次を全文確認して下さい。
    - `.rules/dev/batch/rules_batch_8_code/rules_batch_8_code_html.md`
    - `.rules/dev/batch/rules_batch_8_code/rules_batch_8_code_css.md`
    - `.rules/dev/batch/rules_batch_8_code/rules_batch_8_code_javascript.md`
    - `.rules/dev/batch/rules_batch_8_code/rules_batch_8_code_java.md`
    - `.rules/dev/batch/rules_batch_8_code/rules_batch_8_code_sql.md`
  - 共通規約と対象言語規約で記法、命名、コメントまたはheaderが異なる場合は対象言語規約を優先し、両方を同時に適用してはいけません。
  - 規約の一部だけを確認して、コーディング規約全体を確認済みとしてはいけません。
  - 実装前に、各規約の章・項目について今回の変更への適用有無を判定して下さい。
  - 実装後に、追加・変更した全差分を適用対象となる全規約と照合して下さい。自動確認できない命名、コメント、配置、空行、既存踏襲等も目視確認して下さい。
  - 確認結果には、規約ファイル、章・項目、適用有無、判定、確認根拠を記録して下さい。
  - レビューやユーザ指示によりコードを再修正した場合は、再修正した差分について規約確認をやり直して下さい。
  - 未確認項目または規約違反が1件でもある場合は、コード作成・修正・確認を完了扱いにしてはいけません。
  - コーディング規約の確認だけを目的として、変更対象外の既存コードを一括修正してはいけません。

  対象バージョンにコーディング規約が存在しない、配置が不明、内容が矛盾する、または適用判断ができない場合は、コード変更を開始せずユーザへ報告して下さい。

### 開発種類

  作業は、通常開発、簡易開発および分析の3種類に分かれます。
  - 通常開発: 要件定義から設計、実装、確認までを段階的に行う開発です。開発種類として `batch`、`app`、`class` を使用します。
  - 簡易開発: 軽微な修正などを簡略化した手順で行う開発です。開発種類として `quick_fix` を使用します。
  - 分析: GitHub Actionsを原則の実行基盤、Gitを管理基盤として、一括分析を行います。作業種類として `analyze` を使用します。

### 開発案件ごとの工程成果物管理

  `.document`は単数形を正式名称とし、バージョンごと、開発案件ごとに成果物を管理して下さい。

```text
.document/
└─ v{n}.{m}/
   ├─ 00_全体仕様/
   │  ├─ 00_index.md
   │  ├─ 01_差分仕様.md
   │  ├─ 項目別仕様書
   │  └─ 99_仕様確認.md
   └─ 01_開発案件/
      ├─ 00_開発案件一覧.md
      ├─ 01_完了/
      │  └─ {NN}_{案件名}_v{n}.{m}/
      └─ 02_未完了/
         └─ {NN}_{案件名}_v{n}.{m}/
```

  通常開発の手順1〜2はプロジェクト全体を対象とし、`.document/v{n}.{m}/00_全体仕様/`へ格納して下さい。
  通常開発の手順3〜10は案件別成果物として、`.document/v{n}.{m}/01_開発案件/02_未完了/{NN}_{案件名}_v{n}.{m}/`へ格納して下さい。
  簡易開発の手順1〜3も独立した案件として同じ未完了案件フォルダへ格納し、手順3が合格した時点で完了フォルダへ移動して下さい。

  - `NN`は`01`から始まる2桁の固定案件番号とし、登録順に採番する。
  - 完了、取消または統合後も案件番号を変更・再利用しない。
  - 案件名は対象と目的を識別できる名称とし、同じバージョン内で重複させない。
  - `01_完了/`には、必要な最終工程と確認結果が合格した案件だけを配置する。
  - `02_未完了/`には、未着手、実施中、確認中、保留中または不合格の案件を配置する。
  - 案件完了時は案件フォルダ全体を`02_未完了/`から`01_完了/`へ移動し、全参照リンクを更新する。
  - 手順3以降の成果物をバージョンフォルダ直下、全体仕様フォルダ、別案件またはコードファイル単位のフォルダへ分散させない。
  - 手順8の製品コード、製品データおよび生成結果は案件フォルダへ複製せず、正式な製品配置に置き、案件成果物から対象パスとcommit SHAを参照する。
  - 全案件に共通する仕様変更は案件フォルダだけで完結させず、`00_全体仕様/`の該当仕様へ反映する。

#### `.document`バージョンの更新基準

  `.document/v{n}.{m}`はリリース番号そのものではなく、プロジェクト全体の仕様基準版を表します。対象リリース番号は`00_開発案件一覧.md`へ別項目として記録して下さい。

  - majorの`n`は、アーキテクチャ、主要データ構造、主要処理方式、外部公開契約または開発工程の前提を大きく変更し、従来の全体仕様を同じ基準版として扱えない場合に上げる。
  - minorの`m`は、同じ主要構造を維持したまま、全案件へ適用する機能、画面、データ項目、運用、外部連携または受け入れ条件を追加・変更する場合に上げる。
  - 同じ全体仕様内の案件追加、実装修正、テスト・証跡追加、誤字修正および内容を変えない説明改善では、`v{n}.{m}`を上げない。
  - 案件固有の変更が後続案件にも適用される共通仕様へ発展した場合は、全体仕様へ反映し、minor以上の更新要否を判定する。
  - バージョンを上げる場合は、直前の合格済み全体仕様を継承し、`01_差分仕様.md`へ変更理由、変更範囲、互換性、移行方針および旧版との関係を記録する。
  - 判断が分かれる場合は、既存バージョンへ追記せず、変更対象とmajor/minorの選択肢をユーザへ提示して承認を得る。

#### 開発案件一覧

  `.document/v{n}.{m}/01_開発案件/00_開発案件一覧.md`を案件管理の正本とし、少なくとも次を記録して下さい。

  - 案件番号、案件名、案件フォルダへの相対リンク
  - 開発種類と追加分類
  - 目的、対象リリースまたは比較基準
  - 現在工程、状態、依存案件
  - 対象ブランチ、基準commit SHA、完了commit SHA
  - 使用するチェックリストと確認結果
  - GitHub Actionsを使用する場合の実行先、Run IDおよび成果物

  新規登録、工程承認、保留、再開、完了、取消、分割または統合が発生するたびに一覧を更新して下さい。

#### 開発案件管理チェックリスト

  - [ ] `00_開発案件一覧.md`へ案件を登録したか。
  - [ ] 未完了案件を`02_未完了/{NN}_{案件名}_v{n}.{m}/`へ配置したか。
  - [ ] 対象工程の成果物を同じ案件フォルダへ集約したか。
  - [ ] 全体仕様へ影響する内容を`00_全体仕様/`へ反映したか。
  - [ ] `.document`のバージョンを更新する場合、major/minor基準、継承元および差分仕様を確認したか。
  - [ ] 案件番号を変更または再利用していないか。
  - [ ] 工程、状態、対象ブランチ、commit SHA、チェックリストおよびActions証跡を更新したか。
  - [ ] 完了時に案件フォルダ全体を`01_完了/`へ移動し、全参照リンクを更新したか。

### UIデザイン追加分類

  参照画像、モックアップ、ワイヤーフレーム、画面構造またはレスポンシブレイアウトを扱う`app`開発では、追加分類`ui-design`を適用し、`.rules/dev/app/other/ui/rules_app_ui_design.md`を必ず参照して下さい。
  `ui-design`は独立した開発種類ではなく、`app`の手順1〜10へ追加する必須ルールです。
  作業開始時に`.rules/dev/app/other/ui/app_ui_design_checklist.md`を案件の成果物フォルダへコピーし、各工程の確認結果と証拠を記録して下さい。
  参照資料がある場合、機能維持とレイアウト維持を分け、再現度、UI要件ID、実装前プレビュー承認、画面幅別スクリーンショットおよびユーザの最終目視承認を管理して下さい。
  チェックリストに未確認、未完了またはNGが残る場合、該当工程および最終確認をPASSとしてはいけません。レビューまたはユーザ指示で変更した場合は、影響項目を再確認して下さい。

### リプレース追加分類

  既存の実装、実行基盤、データ処理、状態管理または連携方式を置き換える`app`または`batch`開発では、追加分類`replace`を適用して下さい。
  `replace`は独立した開発種類でも`quick_fix`でもなく、`app`または`batch`の手順1〜10へ追加する必須ルールです。

  - `app + replace`: `.rules/dev/app/other/replace/rules_app_replace.md`と`.rules/dev/app/other/replace/app_replace_checklist.md`を使用する。
  - `batch + replace`: `.rules/dev/batch/other/replace/rules_batch_replace.md`と`.rules/dev/batch/other/replace/batch_replace_checklist.md`を使用する。
  - UIを含むappリプレース: `app + replace + ui-design`として、appリプレースとUIの両方のルールおよびチェックリストを使用する。

  作業開始時に該当チェックリストを案件の成果物フォルダへコピーし、手順1〜10の各工程で更新して下さい。
  チェックリストに未確認、未完了またはNGが残る場合、該当工程および最終確認をPASSとしてはいけません。レビューまたはユーザ指示で変更した場合は、影響項目を再確認して下さい。

### 通常開発

  下記ファイルを順番に作成します。
  {filename}はコードファイル名、{n}はバージョン、{m}はリビジョンになります。
  該当する手順のルールファイルを参照しながら作成を行って下さい。
  - 参照可: 当該工程ルール、共通ルール、直前工程で承認済みの成果物
  - 参照不可: 未承認の途中成果物、他工程の未使用ルール
  - 例外: 通常開発の手順10（最終確認）では、仕様書、手順1〜9で承認済みの全成果物、および各確認結果を参照可とします。

  開発を開始する前に、対象バージョンの`00_全体仕様/`と`01_開発案件/`、開発案件一覧、完了・未完了フォルダおよび対象案件フォルダを作成します。
  手順1〜2の成果物は`00_全体仕様/`、手順3〜10の成果物は対象案件の未完了フォルダへ格納します。
  `.document`または必要なフォルダが存在しない場合は、成果物を作成する前に作成します。
  `.document`フォルダはGit管理対象とします。空フォルダとして保持する必要がある場合は、`.document/.gitkeep`を作成します。

  各手順が終わった時点でユーザに確認を取って下さい。
  手順1が終わったらユーザに確認を取り、問題なければ手順2に進みます。
  手順2が終わったらユーザに確認を取り、問題なければ手順3に進みます。
  以下、同様です。
  処理中に矛盾が見つかった場合は、処理を終了してユーザに報告して下さい。

### 変更区分の独立判定

  `[ADD]`、`[MOD]`、`[DEL]`、`[KEEP]` は、仕様書、基本設計の処理、詳細設計の処理・関数・ロジック・変数、コードの各管理対象について個別に判定して下さい。

  - 上位工程の変更区分を、下位工程の管理対象へ機械的に継承してはいけません。
  - 基本設計の処理 `[Sxxx]` が `[MOD]` でも、その処理から呼ばれる既存関数自体を変更しない場合、当該関数 `[Fxxx]` または `[Txxx]` は `[KEEP]` として下さい。
  - 既存コードを実際に変更する関数だけを `[MOD]`、新規作成する関数だけを `[ADD]`、削除・廃止する関数だけを `[DEL]` として下さい。
  - 処理フローに関係するだけでコードを変更しない関数を、`[MOD]` の実装対象として扱ってはいけません。
  - 詳細設計では現行コードを確認し、実在するファイル、関数、呼び出し元、呼び出し先と変更予定箇所を特定した上で変更区分を決定して下さい。
  - 実装時に変更区分または対象関数の誤りを発見した場合はコード変更を停止し、詳細設計と詳細設計確認を補正してユーザの承認を得てから再開して下さい。

  各ファイル作成後、ログを`.rules/log/rules_{dev}.log`に記述します。
  ファイル作成時に気になることや懸念事項などあれば、質問して構いません。

  `{dev}`は設計書の種類を示しており、
  - batch : バッチ処理用の設計書
  - app   : アプリケーション用の設計書
  - class : クラス設計書（作成中）

  があります。
  最初に、どの設計書を使用するかを確認して下さい。
  以降、その設計書を使用して設計を進めます。
  ルールファイルは、`.rules/dev/{dev}/`フォルダにあります。
  下記の10工程は `app` と `batch` に適用します。`class` の工程変更は保留とし、既存のclassルールに従って下さい。

  |手順|種類|ルールファイル|出力ファイル名|
  |---|---|---|----|
  |1|仕様書作成|`rules_{dev}_1_spec.md`|`.document/v{n}.{m}/00_全体仕様/`の`00_index.md`、`01_差分仕様.md`および項目別仕様書|

### 簡易開発

  簡易開発の手順を以下に示します。

  簡易開発は、軽微な修正、既存仕様の範囲内の不具合修正、文言修正、ログ修正、コメント修正、既存処理の小規模な条件変更などを対象とします。
  仕様変更および仕様書の修正を伴う作業は対象外とし、通常開発を使用します。
  簡易開発では仕様書を作成、変更、削除してはいけません。
  簡易開発の指示があった場合は、こちらに沿って修正を行って下さい。

  下記ファイルを順番に作成します。
  {filename}はコードファイル名、{n}はバージョン、{m}はリビジョンになります。
  該当する手順のルールファイルを参照しながら作成を行って下さい。
  - 参照可: 当該工程ルール、共通ルール、直前工程で承認済みの成果物
  - 参照不可: 未承認の途中成果物、他工程の未使用ルール
  - 例外: 簡易開発の手順3（コード確認）では、既存仕様書、手順1〜2で承認済みの全成果物、および動作確認結果を参照可とします。

  簡易開発を開始する前に、開発案件一覧へ登録し、`.document/v{n}.{m}/01_開発案件/02_未完了/{NN}_{案件名}_v{n}.{m}/`を作成します。
  手順1〜3で作成する成果物は、すべてこの案件フォルダ内に格納します。
  手順3の確認が合格した場合は案件フォルダ全体を`01_完了/`へ移動し、開発案件一覧と参照リンクを更新します。

  各手順が終わった時点でユーザに確認を取って下さい。
  手順1が終わったらユーザに確認を取り、問題なければ手順2に進みます。
  手順2が終わったらユーザに確認を取り、問題なければ手順3に進みます。
  以下、同様です。
  処理中に矛盾が見つかった場合は、処理を終了してユーザに報告して下さい。
  仕様変更の必要性が判明した場合は作業を停止し、通常開発へ切り替えるかユーザへ確認して下さい。
  ユーザが承認した場合のみ、通常開発を手順1から開始して下さい。ユーザの承認を得ずに切り替えてはいけません。

  各ファイル作成後、ログを`.rules/log/rules_quick_fix.log`に記述します。
  ファイル作成時に気になることや懸念事項などあれば、質問して構いません。

  簡易開発では、app / batch 共通のルールとして `.rules/dev/quick_fix/` フォルダ配下のルールファイルを参照します。

  原則として、簡易開発を行う場合はリビジョンを上げます。

  |手順|種類|ルールファイル|出力ファイル名|
  |---|---|---|----|
  |1|修正内容の要件|`rules_quick_fix_1_request.md`|`{filename}_v{n}.{m}_1_request.md`|
  |2|コード修正|`rules_quick_fix_2_code.md`|`{filename}_v{n}.{m}.{code_ext}`|
  |3|コード確認|`rules_quick_fix_3_code_confirm.md`|`{filename}_v{n}.{m}_3_code_confirm.md`|

### 分析

  分析では、条件と全体ワークフローを事前に確定・承認し、その後は重大な停止条件がない限り追加確認を行わず一括実行します。
  GitHub Actionsを原則として使用し、コードでの解析が困難な場合は承認済みworkflowに従ってChatGPT分析または併用分析を行います。

  分析成果物は、対象リポジトリで定めた分析用フォルダへ格納します。
  public/privateの2リポジトリを使用する場合、非公開の条件、コード、入力、詳細結果およびChatGPT分析記録はprivate側を正本とします。
  各工程の成果物作成後、ログを`.rules/log/rules_analyze.log`に記述します。

  |手順|種類|ルールファイル|主な出力|
  |---|---|---|---|
  |1|分析条件定義|`rules_analyze_1_request.md`|`{analysis}_v{n}.{m}_1_request.md`|
  |2|全体ワークフロー設計|`rules_analyze_2_workflow.md`|`{analysis}_v{n}.{m}_2_workflow.md / .json`|
  |3|分析条件・ワークフロー確認|`rules_analyze_3_workflow_confirm.md`|`{analysis}_v{n}.{m}_3_workflow_confirm.md`|
  |4|Actions・分析処理作成|`rules_analyze_4_implementation.md`|workflow、分析コード、`{analysis}_v{n}.{m}_4_implementation.md`|
  |5|一括分析実行|`rules_analyze_5_execute.md`|`{analysis}_v{n}.{m}_5_result.md / .json`、manifest、checkpoint|
  |6|分析結果確認|`rules_analyze_6_result_confirm.md`|`{analysis}_v{n}.{m}_6_result_confirm.md`|

  手順3のユーザ承認後は、停止条件に該当しない限り手順4と手順5を一括して進めます。
  手順6で修正が必要と判明しても、自動的にコードや仕様を変更せず、app、batchまたはquick_fixへの切替についてユーザ確認を取って下さい。
